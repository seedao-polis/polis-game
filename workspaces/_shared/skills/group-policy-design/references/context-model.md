# 上下文模型：记忆命名空间、可见性、隔离与会话

<overview>
这套机制让智能体【记得谁的事、谁读得到、对话不串台】。核心是一张四层命名空间表 + 一道代码层的 Policy Filter + 每 (群, 人) 一份会话。本文是设计记忆隔离边界时的权威参照。
</overview>

<namespaces>
## 四层命名空间（决定【记忆归谁 / 归哪】）

每条记忆必带一个命名空间，无默认值——这是跨人隔离的根。

| 命名空间 | 归属 | 谁读得到 | 典型内容 |
|----------|------|----------|----------|
| `global` | 全局公开 | 任何人、任何群 | 公开知识、人人可见的设定 |
| `group:{chat_id}` | 某个群 | 仅该群内的对话 | 本群共享话题、群内约定 |
| `user:{open_id}` | 某个人 | 该人在**任何群**（跨群通用） | 个人长期偏好、个人事实 |
| `group_user:{chat_id}:{open_id}` | 某群里的某人 | 仅该群里的该人 | 此人在此群的专属上下文 |

**关键**：`user:` 是跨群的——一个人走到哪个群，他的个人记忆都会跟着注入。`group:` 与 `group_user:` 是绑群的，离开这个群就读不到。
</namespaces>

<visibility>
## 可见性与敏感度

每条记忆还带两个标记：

- **visibility（可见性，闸控读取）**：`private`（仅本人）/ `group`（群内）/ `public`（公开）/ `admin_only`（仅管理员）。
- **sensitivity（敏感度，仅影响日志脱敏，不闸模型读取）**：`normal` / `sensitive` / `confidential`。

记住：敏感度**不**决定模型能不能读到，它只影响日志怎么记。真正闸控读取的是命名空间 + 可见性。
</visibility>

<policy_filter>
## Policy Filter = 隔离核心（两道防御）

【谁能读到哪条记忆】由代码算定，模型只拿过滤后的结果。两层：

**第一道：命名空间白名单**

给定 caller 的 `{chatId, userOpenId}`，算出**恰好四个**允许的命名空间：

```
global
group:{chatId}
user:{userOpenId}
group_user:{chatId}:{userOpenId}
```

**永远不含别人的命名空间**——这就是 A 读不到 B 的根因。SQL 查询先用这四个白名单 `WHERE namespace IN (...)` 把别人的行根本捞不出来。

**第二道：可见性闸门（防御性二次过滤）**

捞回来后再过一遍：

1. 命名空间不在白名单的一律剔除（纵深防御，理论上 SQL 已挡住）。
2. `admin_only` 的行：仅当 caller 持管理员标记时放行。
3. `private` 的行：仅本人可见（白名单已保证只有 `user:{本人}` 与 `group_user:{本群}:{本人}` 会进来，所以活下来的 private 必属本人）。

两道防御都在服务端代码里，模型不参与判断、无法自提权。
</policy_filter>

<write_scope>
## 写入归属：自动摘要写去哪

当系统把一个人的近期对话浓缩成长期记忆时，归属由一处统一决策——**一律写 `user:{open_id}` + `private`**（个人记忆、跨群通用、仅本人）。写入点不看群层级，因为分级保密是靠回应时的提示策略实现的，不是靠写入归属实现的。

设计时若要新增【记住某件事】，先问：

```
这件事是…
  人人都该知道的公开知识？        → global,  public
  只在这个群内共享？              → group:{chat},  group / public
  跟着这个人走遍所有群的个人事实？ → user:{open_id},  private
  只在这个群里、只关于这个人？     → group_user:{chat}:{open_id},  private
```
</write_scope>

<budget>
## 注入预算

注入提示时按每域字数预算裁剪，避免提示无限膨胀：群组记忆 ≤ 500 字、个人记忆 ≤ 300 字（超出截断）。设计群组热词、自动摘要这类【会持续增长】的记忆时，要让单条内容控制在预算内，否则会被截断。
</budget>

<session_isolation>
## 会话隔离（对话上下文不串台）

对话上下文按会话键分流：

```
会话键 = {agentId}-{chatId}-{senderOpenId}[-{threadId}]
```

同一个群里，每个人各有一份独立的执行器会话目录与对话历史。所以【机器人在 X 群对甲说的话】和【在 X 群对乙说的话】【在 Y 群对甲说的话】是三段互不污染的上下文。话题（thread）维度可选，开启后同一人在不同话题串也各自独立。

这层隔离是结构性的（不同目录），不需要额外配置；设计时只要知道：**换群、换人，对话上下文就换了一份**。
</session_isolation>

<isolation_summary>
## 两种隔离，强度不同

- **跨【人】隔离 = 硬保证**：命名空间白名单在代码层强制，A 永远读不到 B 的 `user:` / `group_user:`，有测试守。
- **跨【层级】隔离 = 软约束**：个人记忆 `user:` 在任何群都注入；不同密级群之间靠回应时的提示策略约束机器人【别讲上级群的事】，而非在记忆层硬过滤。详见 `tier-policy.md` 的已知限制。

设计时分清这两者：要【某人的隐私不泄漏给另一个人】→ 靠命名空间（硬）；要【公开群别说出工作群的内幕】→ 靠分级提示（软）。
</isolation_summary>
