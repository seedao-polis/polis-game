<essential_principles>
## 这套机制怎么运作

智能体在每个群、对每个人都应表现得不一样：记得的事不同、能说的话不同、对话上下文各自独立。这靠四件东西拼出来——**记忆命名空间**（记得谁的事）、**群组分级**（能对谁说什么）、**系统提示组装**（这两者如何进入提示）、**会话隔离**（对话上下文不串台）。设计这套策略，就是在这四件东西上选定边界与文字。

### 1. 隔离在代码层硬执行，绝不交给模型判断

【这个人能不能看到那条记忆】是先在代码里算好白名单、过滤完再把结果交给模型，模型只拿到过滤后的内容、无从自行提权。设计时永远假设【模型会照单全收它拿到的一切】，安全边界要落在命名空间与可见性闸门上，而不是写进提示里求模型自觉。

### 2. 四层命名空间决定【记忆归谁】

每条记忆必带一个命名空间，决定它归属谁、谁读得到：

- `global` — 公开知识，人人可注入
- `group:{chat_id}` — 本群共享，仅本群可注入
- `user:{open_id}` — 个人记忆，**跨群通用**（这个人走到哪个群都带着）
- `group_user:{chat_id}:{open_id}` — 本群本人专属

**跨人隔离是硬保证**：算白名单时只会给出【当前这个人 / 当前这个群】相关的四个命名空间，永远不含别人的，所以 A 读不到 B。写入必带命名空间、无默认，防止误写成全局而泄漏。

### 3. 群组分级只驱动【回应】，不硬闸记忆

群按运营者手动标记分三级（`public` / `member` / `work`），保密单向向下：低密群不可透露高密群的事。**但这只约束机器人的回应语气与范围（注入一段提示策略），不在记忆层硬过滤个人记忆**——个人记忆 `user:` 在任何群都会注入。这是有意的设计取舍，已知限制见 `references/tier-policy.md`。

### 4. 每个 (群, 人[, 话题]) 一份独立会话

对话上下文按 `会话键 = {agentId}-{chatId}-{senderOpenId}[-{threadId}]` 分流：同一个群里，每个人各有一份执行器会话目录，机器人天然分得清谁是谁、不串台。

### 5. 默认最保守，配置启动时缓存

未显式标记的群一律按 `public`（最保守）。所有策略配置在服务启动时载入并缓存——**改完配置必须重建并重启 serve 才生效**。
</essential_principles>

<context>
当前模型的快照（设计新策略时的参照基线）：

| 设计点 | 现状 / 默认 | 落点 |
|--------|-------------|------|
| 群分级 | `public` / `member` / `work` 三级，运营者手动标 | `configs/chat-policies.json` 每群 `tier` |
| 未标群默认 | `public`（最保守） | 顶层 `defaultTier` |
| 分级政策文字 | 三段内建默认，可逐级覆写 | `tierPolicies`（文件）→ 内建常量 |
| 群专属提示 | 选填，叠在分级政策之后 | 每群 `systemPromptAppend` |
| 记忆命名空间 | `global` / `group:` / `user:` / `group_user:` | 每条记忆的 `namespace` 列 |
| 可见性 | `private` / `group` / `public` / `admin_only` | 每条记忆的 `visibility` 列 |
| 跨人隔离 | 代码层白名单硬保证 | 命名空间白名单 + 可见性闸门 |
| 会话隔离 | 每 (群, 人[, 话题]) 一份 | 会话键 |
| 管理员 | 仅 `admin_only` 记忆放行 | `configs/admins.json` |

身份按 `open_id`：同一人就是同一 `open_id`，他的个人记忆跟着他走遍所有群。
</context>

<assets>
模板在 `templates/`：

- **group-policy-spec.md** — 单个群的策略填空表（层级、受众、可讲、不可讲、语气、专属提示、是否已 listen），并附产出的配置条目形状。
- **context-matrix.md** — (群 × 人) 应对矩阵 + 记忆落位计划表（要记的事 → 归哪个命名空间 → 可见性 → 谁读得到）。

脚本在 `scripts/`：

- **preview_policy.py** — 离线策略模拟器（纯标准库，不读写库、不联网）。给一份群与记忆的规格，站在某 (群, 人) 视角打印可读命名空间、群层级、实际会注入的记忆，并能 `--compare` 两个人证明 A 看不到 B。设计阶段先用它验证隔离，再动真配置。
</assets>

<success_criteria>
一份合格的多人多群组应对策略：
- 每个涉及的群都有明确层级，且说明了【可讲 / 不可讲 / 语气】。
- 群专属提示（若有）只写本群独有规则，不重复分级政策、不重复人格、≤100 字。
- 每条要记住的事都指定了命名空间与可见性，并说明了【谁会读到】。
- 跨人隔离经过验证：用 `scripts/preview_policy.py` 或 `agent memory preview` 证明 A 看不到 B。
- 所有写入都带命名空间，没有【误写全局】的设计。
- 给了每个改动的代码 / 配置落点，并提醒【改完要重建 + 重启 serve】与【把群加进 `listen`】。
- 除非用户明确要求，停在【方案 + 落点 + 验证清单】，不直接改配置、不改库、不发通知。
</success_criteria>
