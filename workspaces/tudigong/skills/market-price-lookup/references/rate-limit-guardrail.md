# 本地限流与防封纪律

East Money 的接口按 IP 做风控，高频会**临时封 IP**（表现为请求直接连不上/超时，不是返回错误码）。本 skill 自带一个**跨进程的本地限流器**，主动把请求速率压在封禁阈值之下，避免撞线。

## 东财风控阈值（经验值，触碰任一即可能被临时封）

- 每秒 > 5 次
- 并发 ≥ 10
- 1 分钟 ≥ 200 次
- 5 分钟 ≥ 300 次

## 本地限流器怎么工作（`scripts/rate-limiter.mjs`）

关键点：每次调用 skill 都是**独立的 `node` 进程**，进程内的节流管不到「同时冒出来的另一次调用」。所以限流器把状态**落到机器级的文件**，让所有进程共享：

- **状态文件**：`<系统临时目录>/eastmoney-ratelimit/reservations.json`，存最近的「已预约发送时刻」滑动窗口。
- **锁**：同目录下的 `lock`（用 `mkdir` 原子占用）。每个进程先抢锁，在锁内**预约**一个未来的发送时刻，写回文件，再放锁、睡到该时刻才真正发请求。于是并发的多个进程会在锁上串行、各自拿到**互不重叠、依次错开**的时段。
- **作用域是每台机器**（东财按 IP 封），不区分 soul / skill / 聊天——全机器共用一份节流账本。
- **保底约束（默认值，都压在封禁线以下）**：
  - 两次请求最小间隔 `1200ms`（封禁线是 >5/s）。
  - 每分钟 ≤ `30` 次（封禁线 ≥200/min）。
  - 每 5 分钟 ≤ `120` 次（封禁线 ≥300/5min）。
- **故障保护**：抢锁超过 20 秒失败就 fail-open（不再死等，仍加一个最小间隔再发），避免卡死的锁把所有查询拖住；崩溃残留的锁超过 10 秒会被自动回收。
- **可用环境变量覆写**（一般不用动）：`EM_MIN_INTERVAL_MS`、`EM_CAP_PER_MIN`、`EM_CAP_PER_5MIN`、`EM_RATELIMIT_DIR`、`EM_TIMEOUT_MS`、`EM_MAX_ATTEMPTS`。批量场景想更保守就调大间隔/调小上限。

实测：4 个进程同时各预约一个时段，拿到的发送时刻精确间隔 1200ms，验证了跨进程串行有效。

## 给 agent 的使用规则

1. **限流器会自动排队**，你不用手动 sleep；但也别故意写循环把几十个标的一次性全查——那只会让每次查询排在很后面、变很慢。
2. **一次问答查 1~3 个标的**就够了。要对比更多，分几轮慢慢来。
3. **`push2`（即时）与 `push2his`（K 线）是不同主机**，其中一个暂时不可用另一个常仍能用——**`quote` 已内建自动回退**：实时(push2)拿不到就自动取最近交易日 K 线收盘、回 `source:"daily-close"`（带 `stale:true`、`asOf` 日期），回答时如实说明是收盘价非实时。单次请求超时默认 20 秒（东财拥堵时只是慢不是死，够它回；env `EM_TIMEOUT_MS` 可调）。
4. **脚本回 `{"ok":false,"reason":"error"}`（如 `message:"fetch failed"` / `"operation was aborted"`）时**，多半是网络波动或 IP 已被在先前限流。如实告诉用户「行情源暂时不可用，稍后再试」，**绝不臆测或编造数字**；隔一会儿再试（限流器会自动错开）。
